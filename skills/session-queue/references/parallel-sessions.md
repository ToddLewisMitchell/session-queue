# Running a parallel session (workflow 4)

Read this before starting a parallel session: `parallel-session <id>`, `next-session` beside a session in the main checkout (workflow 3, step 1), a yes to an offer, or Parallels `auto`. Section and workflow numbers refer to `SKILL.md`; eligibility is in its workflow 4.

1. **Get a worktree on branch `q/<id>-<slug>`,** `<main>` being the default branch. First, unless `git check-ignore -q .claude/worktrees/x` succeeds, add `.claude/worktrees/` to `$(git rev-parse --git-common-dir)/info/exclude` (local, never committed), so worktree files don't show as untracked in the main checkout.
   - **Typed in a new conversation** (either command): make it with git at `.claude/worktrees/<id>-<slug>` in the main checkout, then `EnterWorktree` with its `path` (this conversation becomes the parallel session). Not `EnterWorktree` with a `name`: it makes a generated branch, by default off `origin` (which may be behind main or missing), and can't reopen a branch.
     - The branch is in `git worktree list` (a `PAUSED` row whose work stayed in its worktree): use that worktree.
     - The branch exists without a worktree (a `PAUSED` row's work-in-progress commit): `git worktree add .claude/worktrees/<id>-<slug> q/<id>-<slug>`.
     - Otherwise: `git worktree add -b q/<id>-<slug> .claude/worktrees/<id>-<slug> <main>`.
   - **From the conversation already running a session:** a background agent with `isolation: "worktree"`. It can write only in its generated worktree, which may start off `origin`, behind main, so make it no worktree with git and never use `EnterWorktree` (refused in the agent; here it would move the current session). Its prompt starts with `git switch -c q/<id>-<slug> <main>` (`git switch q/<id>-<slug>` for a `PAUSED` row's branch) and `git log -1` to confirm the base; if the switch is refused, `git checkout --detach <main>`, said in its report. A `PAUSED` row whose work stayed in a worktree can't run this way: offer it for a new conversation. The agent leaves its work uncommitted, since it can't ask for approval (see step 5).
2. Apply the queue's **Worktree setup**.
3. **Edit the queue and topic file in the main checkout by full path, touching only this session's row.** Claim it first (`IN PROGRESS`, see Status); for a background agent, the conversation that launched it does this, under its own name. This applies whether or not the queue folder is committed: an untracked one isn't in the worktree, and editing a committed one's copy in the worktree conflicts at merge. Leave memory alone: the handoff goes in the session notes (Principle 7).
4. Run the Checks in the worktree. If one fails while another session is running, rerun it before blaming that session.
5. **A background agent's work:** when it finishes, this session sends the notify if it's on, shows the diff and the Checks results, proposes a commit message, and after approval (or as **Commits** `auto` allows) commits in the agent's worktree (if the agent stayed detached, `git -C <its worktree> switch -c q/<id>-<slug>` first).
6. **Merge only with approval** (or as **Commits** `auto` allows), after the main session has committed, by the branch-per-session steps in every mode (`--no-ff`, rerun the Checks on the merged result), merging into main from the main checkout (if this conversation is in the worktree, `ExitWorktree` with `keep` first). In a committed queue folder, this session's row and topic file edits are still uncommitted in the main checkout: merge with `--no-commit`, mark the row DONE, stage only this session's edits (`git add -p`), commit, then record the merge commit's hash in the row (see Status in `SKILL.md`). Then `git worktree remove` the worktree (`ExitWorktree` won't remove one entered by `path`; an agent's is locked, so `git worktree unlock` it first), and only then delete the branch, since git won't delete a branch a worktree has checked out. For an agent, also delete its generated branch (`worktree-agent-…`) with `git branch -d`.
